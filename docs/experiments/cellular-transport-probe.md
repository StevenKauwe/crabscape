# Cellular transport probe

The optional `cellular-transport-probe` build feature exercises checkpoint and frame packets over the existing WebRTC connection in independent, actor-free shadow simulations. It does not enable cellular co-op, modify either player's simulation, or provide a UI. Run the `cell-probe`, `cell-probe-loss`, and `cell-probe-disconnect` scenarios of `cargo cooptest` explicitly against a build with this feature; they are excluded from the default scenario selection. The latter two deliberately drop acknowledgements in the guest's test session storage.

Each outgoing checkpoint fragment or frame requires an acknowledgement from the selected transport connection before another can be sent. A missing acknowledgement stalls the producer and eventually aborts it. The connection, current host selection, transfer ID and frame epoch and sequence are checked; disconnect and host changes abandon the shadow session. A producer must stop rather than continue simulating while a frame is outstanding.

This is an experiment, not a playable networking protocol. It does not address input sequencing, actors, guest prediction, reconciliation, migration, replay, or cellular gameplay. The existing transport has unbounded inbound buffering; this outbound stop-and-wait probe is not a denial-of-service or memory bound. Checkpoint capture and decoding still create substantial whole-world copies and may inflate up to 64 MiB; they need bounded, chunk-scoped streaming and browser memory measurements before runtime use. Main-thread compression and round-trip latency also make this unsuitable for live gameplay.

On a local two-Chrome run, the 1,331,987-byte test-level checkpoint required 332 fragments and one terrain frame; the entire test including browser startup and connecting took 55 seconds. This is not an RTT measurement. A bounded sliding window has not been evaluated, and the stop-and-wait result should not be used as an estimate of its performance.
