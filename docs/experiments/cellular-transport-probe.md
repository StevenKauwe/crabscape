# Cellular transport probe

The optional `cellular-transport-probe` build feature exercises checkpoint and frame packets over the existing WebRTC connection in independent, actor-free shadow simulations. It does not enable cellular co-op, modify either player's simulation, or provide a UI. Run the `cell-probe`, `cell-probe-window`, `cell-probe-loss`, and `cell-probe-disconnect` scenarios of `cargo cooptest` explicitly against a build with this feature; they are excluded from the default scenario selection. The last two deliberately drop acknowledgements in the guest's test session storage.

The checkpoint sender permits at most eight 4 KiB fragments outstanding (32 KiB of packet payload). It tracks acknowledgements from the selected transport connection, including reordered ones, and never opens a hole past a missing ACK; it stalls and eventually aborts on loss. A single frame can be outstanding, and a producer must stop rather than continue simulating while it awaits acknowledgement. Connection, current host selection, transfer ID and frame epoch and sequence are checked; disconnect and host changes abandon the shadow session.

On one local two-Chrome run, a 1,331,987-byte test-level checkpoint required 332 fragments and one terrain frame. Measured from the first checkpoint send to the final frame acknowledgement, a one-fragment window took 49.23 seconds and an eight-fragment window took 6.48 seconds, about 7.6 times faster. The 148 ms average per stop-and-wait exchange includes game-loop scheduling and is not a network RTT measurement. These single desktop observations do not establish phone performance.

The browser callback diverts tagged probe packets into a queue before copying their ArrayBuffers into Rust. The queue accepts at most 16 packets of at most 4096 bytes each (64 KiB payload total), and only from currently connected transport peers; the application then checks selected-host identity and validates the decoded message. Full queues and oversized probe messages are dropped, causing the probe to time out rather than grow a backlog. Disconnect and link teardown purge that connection's queued packets. The high-water figure counts queued probe payload, not allocation overhead, already-drained messages, browser-internal buffers, or decoded snapshots. This developer-only queue assumes one active socket per page. In a local two-Chrome run of the eight-fragment transfer, measured high-water queued payload was 32 bytes on the host and 32,280 bytes on the guest; this is one desktop observation, not a phone memory measurement.

This is an experiment, not a playable networking protocol. It does not address input sequencing, actors, guest prediction, reconciliation, migration, replay, or cellular gameplay. Ordinary Matchbox messages and browser-internal buffering remain unbounded; the probe queue and outbound window are not a denial-of-service or overall memory bound. Checkpoint capture and decoding still create substantial whole-world copies and may inflate up to 64 MiB; they need bounded, chunk-scoped streaming and browser memory measurements before runtime use. Main-thread compression and round-trip latency also make this unsuitable for live gameplay.

The local browser run covered completion, dropped acknowledgements, and disconnect for the windowed build. A late duplicate checkpoint ACK arriving after the frame phase begins was guarded and verified in a native two-shadow test after that browser build; that particular guard was not retested in the browser run.

The bounded-ingress browser scenarios were run with voice off. The guard excluding the separate voice channel was added during the release build and was not separately exercised in a voice-enabled browser test.
