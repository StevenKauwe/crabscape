# Cellular co-op: state and mutation coverage

This inventory is a design aid, not a claim that cellular co-op is playable. The normal co-op guard and per-tick full verification remain in place. The existing actor probe is a four-tick disposable sandbox, with no real controls, enemies, recovery or live-world changes.

## The transaction that must agree

The simulation uses a 120 Hz game clock; the material field normally advances every fourth tick. `src/player.rs::simulate` can run up to a quarter-second of catch-up in one rendered frame. The current sandbox calls `Sim::tick_inner` with externally stepped terrain, but still executes shared-world, actor, combat and networking logic. A future transaction must stage the accepted inputs, both clocks, terrain, actors, relevant shared state, random state, events and outbound messages together. An error after a terrain write or actor tick must not publish any of them. A message already sent cannot be rolled back, so externally visible events need bounded staging and idempotent identifiers, or publication only after authoritative confirmation.

At minimum, the host must own and order these state transitions:

- **Detailed terrain:** cells, flow vectors, suspended flags, grain classes and pebble ownership; aggregate positions and motion; sediment parameters; crab and other body reservations. Upward clearing can happen on every game tick, while digging, walking brushes, swimming wakes and most sediment changes run on material ticks. Flow, density, mud cohesion and pebble motion interact, so a single untracked write can affect later terrain.
- **Window and sleeping terrain:** origin, stored world-coordinate chunks, edge opening, seeded-chunk registry, active/sleeping transitions and aggregate integrity. `follow_player`, `shift_window` and far-pebble seeding can change the field even when the material clock does not advance. A commitment must identify chunks by world coordinates, not temporary window offsets, and make each transition atomic.
- **Water-dependent growth and particles:** giant kelp position, velocity and base influence actual climbing through `Level::climb_at` and must remain in authoritative gameplay state. The currently observed tracer, bubble and fine-silt reads feed presentation, but they are still in checkpoints and the existing exact digest. Treating them as local cosmetics requires a separate proof that they cannot feed gameplay and an explicit save/replay compatibility policy; it must not silently change the current verifier.
- **Players and environment:** each crab's controls and press edges, mover, fighter, pending/current events, progress, inventory, memory and relevant timers. `tick_inner` also changes tide, shared resources, nets, rocks and output queues. The host-owned guest shadow in the sandbox covers only restricted actions and trusted initial actors, not complete user state.
- **Creatures:** enemy ordering, ownership, full state, random-generator state, targeting, interactions and handover. The current enemy loop can move sediment and water, use the RNG, update moray homes and prey, and generate combat or network events. Running an enemy twice or omitting its wake changes the shared field.

Private guest `OwnWorld` and local-only persistence are not host terrain: joining, disconnect, host change, failed resync and migration must restore them without exposing an intermediate host state to saving or replay. A source `Peer` must be derived from the actual connection, with duplicate player claims rejected. The starting commitment must bind the rules/tuning and level identity, complete initial terrain and sleeping state, both clocks and phase, actor initial state, RNG, and session epoch. An initial digest is not an ongoing certificate: a regression shows later unrelated corruption can survive a valid scoped scoop.

## A possible path within the budget

At 120 Hz the entire simulation has 8.33 ms per game tick before rendering and browser overhead; a material operation every fourth tick does not get an unconstrained 33 ms on the main thread. In the current desktop Chrome probe, four host callbacks totaled about 70 ms and four guest callbacks about 54 ms; their largest individual callbacks were about 41 ms and 32 ms respectively. One extra full checkpoint digest was about 6.5 ms on each side. These are a few local, voice-off samples, not phone, WAN or percentile measurements.

1. **Enforce a write boundary before trusting incremental state.** Replace direct mutable access to authoritative state with an owned transaction API that records every change or marks every affected world-coordinate leaf. Constructors, restore, streaming, particle/aggregate transitions and error paths must use it too. A root updated from only some writes can remain stale while the underlying state diverges. The test-only opaque scoop owner proves a limited ownership shape, not this whole-world invariant.
2. **Start from a verified complete root and update it transactionally.** Use canonical encoding and a collision-resistant, domain-separated tree with stable chunk keys and separately committed metadata/actor leaves. Exact source-bound commands and checked root/sequence must agree before commit. A periodic full scan can audit the implementation, but it must not be the only way missed writes are detected. Preserve old versions or an undo journal until actor, terrain and outbox work all succeed; cap retained versions and fail closed on overflow.
3. **Avoid materializing and copying the full window on every operation.** Current guarded paths construct chunk fields from contiguous arrays, clone them and copy them back; merely hashing fewer cells does not remove those costs. The unwired immutable chunk-version experiment can share snapshots, but does not implement the game's update order, paging, CPU budget or mutation coverage. A direct chunk implementation must first match solo ordering, seams, reservations, pebble atomicity and conservation for the same region.
4. **Treat dense material ticks separately.** In one opening fixture, a sparse upward off-material scoop touched 2 of 60 tiles while diffusion changed 53. A scratch native BLAKE3 benchmark on five terrain arrays measured about 0.345 ms for two leaves plus tree rebuild and 9.254 ms for all 60 leaves (30 samples). It omitted globals, mutation tracking, sleeping chunks, actors, network, rendering and Wasm/phone costs; it is not an end-to-end budget result. Dense material work may still need a different representation or cadence that preserves observable physics.
5. **Build actual bounded pacing and reconciliation.** `take_in` runs in the app input set, `simulate` loops ticks, and `send_out` follows simulation. A four-input predeclared batch only shows that a bounded sandbox can avoid one reply per tick; it does not predict changing controls. Real controls need source-bound tick/edge sequencing, a bounded prediction horizon, authoritative actor reconciliation, bounded rollback and a safe freeze/resync or private-world restoration on gaps, queue overflow or host change. Never accumulate unbounded catch-up work while waiting.
6. **Measure before lifting the guard.** Compare host and guest p50/p95/p99 and worst-case time, allocations and retained/peak memory on real map regions, material/off-material ticks, multiple nearby and separated animals, window shifts, loss/reordering, browser background/resume and target phones. The current sample event journal is 6,351 bytes for one pebble+wake operation; at 120 such ticks per second that hypothetical payload alone is roughly 6.10 Mbit/s per guest. It must not be treated as a measured average or a usable protocol.

The test-only `ScoopVerifier` now owns its restricted `ChunkFlow` in a private child module and exposes no mutable reference to it. Independent compile-fail checks confirmed that callers cannot access its field, mutate through the accessor or construct the owner unchecked; two-step rollback/retry also passed. This is a useful ownership boundary for that single-scoop experiment, not for live World, actor, streaming, material-step or transport state. Its internal fault-injection regression still demonstrates that an initial token cannot detect later unrelated corruption, and complete mutation instrumentation remains a prerequisite.
