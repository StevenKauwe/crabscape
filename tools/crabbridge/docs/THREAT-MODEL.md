# Threat model and launch gates

## Trust boundary
The Mac owner/admin, registration files, executable binaries, frontend assets, and local OS are trusted. Browser request fields, model/tool output, other websites, and future signaling/TURN servers are untrusted. A password-authenticated control user has terminal input authority to exactly their host-registered tool choices, including answering the tool's permission prompts. This can be broad host authority if the tool itself is privileged.

## Enforced now
- Local HTTP gateway has a hard loopback bind; exact Host/Origin and same-origin fetch context protect against ordinary cross-site browser invocation and DNS rebinding. These headers are not authentication against native clients.
- Passwords verified using Argon2id defaults with random salt; hashes reside in local config. Temporary bearer tokens are 256-bit random; server stores only SHA-256 digests. They stay in browser JS memory, never URL/storage/cookies. Restart invalidates that process’s sessions. Every production gateway/peer checks its exact host-config snapshot before accepting authority and on a 500 ms idle poll. Observed content, identity, symlink, metadata changes or read failure permanently revoke that snapshot, dropping sessions; restoring old bytes does not reactivate it. Admin writes through aliases update the canonical target. This is bounded regular-file observation, not atomic cross-process revocation or live config reload. Restart each process to accept new config.
- Global five login attempts per minute; eight sessions maximum. It trades availability for fail-closed behavior. Usernames are not secret; timing may reveal valid usernames. Password lengths 16..1024 bytes.
- Strict serde schemas, body limit, per-session request counters and session ownership. Replayed commands rejected. Connection loss may require reauthentication, not blind retry.
- No shell interpolation. Tool path/args/workspace come only from admin config. Passworded browser cannot register tools, pick cwd, or inject arguments.
- Tool output is parsed by pinned vendored xterm.js, not inserted as HTML; active OSC8 links are disabled. No clipboard addon. CSP permits local scripts/WASM and inline styles needed by the terminal, but no remote script dependencies. Terminal parsing remains an additional library attack surface. Tool output is untrusted.

## Not security guarantees
CWD is not a sandbox. Terminal users can instruct Codex to access any files/commands its policy permits. They can approve Codex prompts. Never advertise a narrower sandbox than the child actually provides. Tool arguments can deliberately configure dangerous permissions; only trusted admins may choose them. Local HTTP is not safe to expose remotely. A compromised host, browser extension, frontend build or client device can steal session authority. Heap secrets are not securely erased. Per-request timing protection, credential recovery, user audit and full lifecycle isolation need further review.

PTY input uses a bounded eight-message worker queue; full queues fail without blocking request processing. Revocation detaches child kill/reap from the state lock. A non-reading child has an adversarial logout test. Process spawning runs outside the session lock with a reserved launch slot; canceled/expired launches cannot acquire session authority. Spawn workers still need bounded OS-level timeout supervision before remote operation. Output readers are bounded in memory but lifetime/descendant cleanup needs stronger supervision. One controlled PTY per App/process is a logical limit, not a guaranteed OS-process count: Stop releases the slot before detached cleanup finishes, and separate remote-answer processes have separate limits. A per-process budget of sixteen PTY lifecycles now includes active tools, detached immediate-child cleanup and blocked I/O workers; slots release only after all of these exit. This bounds rapid Stop/Start worker accumulation and fails new launches closed if stuck workers fill the budget. It is not a host-wide budget across multiple gateway processes, and it does not kill daemonized descendants. A shared host-wide budget and stronger containment remain required before external exposure. This is a local engineering prototype, not a public service.

## Integrated loopback peer proof

The root remote-answer command consumes a fresh per-user/session invitation into a per-config ledger keyed by the cryptographic session ID. Snow Noise NNpsk0 authenticates the random 256-bit private capability and encrypts all application traffic above WebRTC. Canonical host/principal/session/expiry context is bound to the handshake. The fixed principal then authenticates by password inside that channel; it cannot select another identity. No local bearer token is returned. Connection-owned sessions are tracked by immutable grant ID and cleaned even if response delivery or caller future is canceled. Command acceptance and launch installation recheck closed/expiry state under lock. Native ICE defaults remain loopback-only; the separately selected LAN and DirectStun profiles below are explicit exceptions.

## Remote milestone gate
Before external exposure: independently review the high-entropy pairing composition (or choose reviewed OPAQUE for a human-password-only flow); bind authentication to both peers and command transport, prevent hostile signaling MITM, derive authenticated encryption using existing implementations, test tampering/replay/wrong-password/session theft/revocation and concurrent approvals. WebRTC DTLS alone is transport encryption, not human identity verification. TURN must relay encrypted application content. Use private trusted frontend delivery, no CDN code. Separate ordinary tool control from structured approval capabilities only via a verified app-server adapter, never string matching terminal output.

## Automatic local signaling
The optional one-room broker binds only 127.0.0.1:7879. It knows independent random host/browser role credentials, expiry and SDP, not the Noise invitation secret or user password. Browser origin is exactly the trusted frontend 127.0.0.1:7878; the native host has a fixed destination and disables proxies and redirects. Authenticated endpoint context and terminal authorization remain inside Noise and the host, not the broker. SDP schemas, UTF-8 byte sizes and encoded-envelope bounds are enforced on both sides because signaling is untrusted. Retrieval is one-use, so response loss fails closed and requires fresh pairing. This is not public rendezvous deployment, an HTTPS trust story, or proof of separate-device connectivity.

## Existing CrabScape introducer and scoped LAN exception

The default local HTTP/ICE boundaries above remain unchanged. The separately authorized fixed-address LAN pilot in `VERIFICATION.md` is an explicit exception, not a wildcard/public listener. The newer Matchbox adapter contacts only the exact host-selected CrabScape WSS endpoint or the explicit loopback test endpoint. It does not make the native ICE policy nonloopback by itself.

CrabScape's public introducer has no CrabBridge role authentication. Its room IDs, peer IDs and ready messages are untrusted negotiation metadata. Public-room participants or the server can deny service, occupy the selected peer, inject SDP or burn a pairing attempt. They cannot thereby authenticate the Noise channel, see the password, select a principal, or execute a tool. Capabilities/passwords/terminal traffic are never serialized into signaling. Browser and native adapters strictly bound schemas, UTF-8 SDP size, frame/event counts, lifetimes and sender identity within a single attempt. A wrong-capability browser through the actual local Matchbox implementation is a repeatable rejected-authentication case. This does not prove availability against a malicious server or all protocol failures.

Publishing the trusted frontend under `/crabbridge/` on the existing game origin would share that origin's publisher, scripts, storage and service-worker trust. A path is not an origin isolation boundary. Public source integration and allowlisted asset packaging are not authorization to deploy or enable remote host networking. Before publishing, review the root service worker and hosting headers, use a restrictive CSP with the exact rendezvous origin, and choose explicitly whether the shared-origin trust is acceptable. A separate origin offers stronger isolation but does not require a separate rendezvous service.

## Explicit Internet discovery profile

`remote-direct` and a Noise-bound `direct-stun-v1` invitation opt into standard WebRTC wildcard ephemeral UDP and fixed Google STUN discovery. SDP validation bounds advertised candidates; it is **not a datagram firewall**, and peer-reflexive/inbound traffic remains possible. No TURN is configured. Both this activation and actual deployment require owner authorization. The local aggregate does not contact STUN or prove carrier connectivity. See `direct-stun-host.md`.
