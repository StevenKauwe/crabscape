# Security architecture review

Date: 2026-11-12. Scope: local Codex Harbor prototype, integrated native/browser WebRTC gateway, automatic loopback signaling, the explicitly authorized temporary two-device LAN pilot, the CrabScape Matchbox adapter/public-source integration, source-only static composition/hosting safeguards, and optional passkey authentication tested locally. This is an internal engineering review, not an external security audit, penetration-test certification, or approval for public deployment.

## Recommended security model

The host's owner is the administrator. Only host-side administration may register executable paths, fixed arguments, initial working directories, users, and tool grants. A remote browser must never supply these values or an arbitrary request path, RPC method, environment, or child-process command line.

An authenticated principal may control only its own session and host-granted registrations. Raw terminal control necessarily includes responding to the registered tool's approval prompts. Codex's existing permissions remain authoritative. A starting directory, tool allowlist, or transport encryption does not add a filesystem sandbox. Tools run with the host process's OS identity and may access anything their own policy permits. Use this prototype only for trusted users and trusted registered tools.

A browser terminal must treat tool output as untrusted. Use a local pinned terminal implementation, disable active links and optional clipboard/file integrations, preserve bytes across output chunks, and never turn terminal text into HTML or interpret it as application authorization.

## Authentication and transport

The local HTTP service remains hard-bound to loopback with exact Host/Origin checks. Those headers defend browser-origin attacks, not native local attackers. Keep local endpoints local; exposing or reverse-proxying them does not create a remote security boundary.

The transport uses the established `snow` implementation of `Noise_NNpsk0_25519_ChaChaPoly_BLAKE2s` over a reliable, ordered WebRTC data channel. The PSK must be a fresh cryptographically random 256-bit capability, not a human password or a hash of one. Standard WebRTC DTLS does not authenticate the human or the intended host. Every application frame must remain inside Noise; signaling must not be able to change authenticated commands.

The Noise prologue binds protocol purpose/version and canonical host, principal, session, and expiry context. These values must come from the host's trusted invitation, not an unverified browser assertion. The capability and context require trusted out-of-band delivery. A public room code is only rendezvous metadata.

NNpsk0 provides symmetric possession-based authentication: anyone holding a capability can act as either endpoint for that capability. Never share one key across principals. A fresh private capability per principal/session plus the host-configured password inside the encrypted channel is an acceptable local integration experiment, not password-only pairing or a complete device-identity system. Use reviewed PAKE or a reviewed device-authentication design for a production password-only/persistent pairing feature. Do not invent password-to-key derivation, handshakes, or encryption primitives.

The application gateway should be a closed typed protocol: connection-bound login, terminal operations, and logout. The host fixes the principal. The browser cannot choose a username, bearer token, URL, headers, registration, or authorization context. The same authorization core must enforce both HTTP and WebRTC operations. Remote session tokens stay inside the host.

## Required lifecycle invariants

1. A launch has a unique reservation identity. Stop/revoke cannot allow an old completion to attach to a later launch. A canceled launch continues occupying its global resource slot until its actual worker finishes.
2. An owned supervisor, not the request's lifetime, clears the reservation and disposes of stale results. Dropping an HTTP/WebRTC waiter must not strand the launch slot.
3. Fallible PTY descriptor and worker preparation occurs before the child is spawned, or an RAII guard must kill/reap a child after any setup error.
4. Revocation removes input authority immediately and never waits on a blocked PTY write. Input and output are bounded. Child cleanup is supervised separately from the session lock.
5. Logout, tool replacement, expiry, and identity changes clear queued input. Authentication transitions clear displayed output/scrollback too. In-flight browser responses carry a generation and cannot mutate a newer session.
6. A connection close, protocol/authentication failure, expiry, or explicit revoke marks the connection closed before cleanup. No login completing afterward may install an untracked session. Every remote-created session must remain attributable to its connection/grant for cleanup, including canceled response delivery.
7. Cancellation observes the current closed state, not only a future change notification. Absolute expiry includes time spent gathering candidates/handshaking. The command core rechecks liveness before accepting work.
8. Output cursors advance only by bytes actually returned. Output limits apply to encoded protocol frames, not just raw PTY bytes.
9. Reconnection never replays input automatically. Lost responses require reconciliation or reauthentication, not blind command retries.

## Findings from this review

The following were reported to the implementation owner and fixes were reviewed in source during this pass. Final test evidence is recorded here and in `VERIFICATION.md`; no completed external attack assessment is implied.

- **Stale launch attachment:** a boolean `launching` flag allowed Start A / Stop / Start B to confuse ownership. Changed to unique launch IDs plus a global outstanding-worker reservation.
- **Canceled waiter resource leak:** reservation cleanup lived after the HTTP handler's blocking-task await. Changed to an owned launch supervisor; a dropped-waiter regression test was added.
- **Cross-session queued input:** the browser retained buffered input across tool/identity transitions. Changed to explicit resets and in-flight generation guards; corresponding remote-UI safeguards and disposal/recreation of xterm on identity transitions prevent pending old render writes from reappearing.
- **Partial PTY startup orphan:** child launch preceded fallible PTY handle creation. Those preparation steps and fallible worker creation were moved ahead of process spawning.
- **Hidden wildcard UDP listener:** the WebRTC ICE dependency defaults to mDNS QueryOnly, which binds `0.0.0.0:5353` on macOS. Loopback candidate filtering alone did not disable it. Explicit mDNS Disabled was added; verify actual sockets during every relevant smoke test.
- **Channel-close revocation gap:** closing only the data channel did not necessarily close the peer connection. Explicit channel-close/send-failure cancellation and rejection of partial-reliability channels were added. Current-state cancellation, absolute deadlines, fatal-error signaling, and command-core grant-expiry/revocation rechecks were subsequently added.
- **Reusable capability terminology:** a key file by itself is reusable across process invocations. The integrated gateway added an atomic consumed-grant marker indexed by session ID in a host-config-scoped ledger; the standalone echo spike still permits key reuse until expiry. Treat deleting/moving the ledger or cloning the host configuration as administrative actions that can reset this boundary. Single accepted data channel per process is not, by itself, durable one-use pairing.
- **HEAD consumed one-use signaling:** Axum implicitly dispatches HEAD through a GET handler. The broker originally consumed the SDP even though the response body would be omitted. An explicit GET/POST method gate now precedes room mutation; offer and answer regressions verify that HEAD leaves the message available to its authorized GET consumer.
- **Signaling endpoint validation:** the native receiver originally passed a broad RTC description directly to the WebRTC library, and the browser measured SDP in UTF-16 code units rather than UTF-8 bytes. Both endpoints now independently validate the expected description type, closed field set, SDP prefix/NUL restrictions, and 64 KiB byte cap before use. The native DTO also rejects duplicate fields. The JSON envelope limit is aligned with the broker's bounded escaped representation; broker validation alone is not trusted by the endpoints.

## Additional snapshot-revocation hardening

The gateway now binds every production App to the exact bytes it parsed from a host-owned configuration file. The guard records SHA-256 plus file identity/change metadata, the absolute caller path, its entry identity, and the canonical target. Reads are limited to a regular file of at most 1 MiB; nonblocking/no-follow opening and before/after identity checks reject file-type or path replacement rather than waiting on a replacement FIFO. Local filesystems and local administrators remain trusted.

Login acceptance, authenticated-session installation, terminal commands, preview requests, and late launch installation recheck the guard while holding the application's authority lock. A read failure or observed change permanently revokes that process's snapshot, marks remote sessions closed, and drops session-owned terminals. Restoration of the old bytes does not revive the revoked process. Restart explicitly captures a new snapshot. Existing admin saves resolve the canonical target once, so changing a shared configuration through a symlink alias updates the shared file instead of silently replacing only the alias.

Both HTTP and remote-answer own a 500 ms idle sweep. Dropping the owning scope aborts the watcher rather than retaining an App forever. Independent processes observe the same filesystem separately: the polling interval is not a real-time guarantee, and there is no atomic transaction with administrative edits or already-accepted tool work. Brief unobserved filesystem changes are not universally detectable. This mechanism revokes old snapshots; it does not implement live permission reload, instantaneous global cancellation, rollback, or guaranteed descendant termination.

## Automatic local signaling review

The new broker is a single ephemeral room bound to `127.0.0.1:7879`. Separate random 256-bit client and host bearer credentials authorize only their respective offer/answer operations. They are not the Noise capability and confer no CLI authority. The broker enforces exact Host and browser Origin, closed JSON descriptions, 64 KiB SDP byte limits, one-use ordered message consumption, a five-second body deadline, a per-broker 16-request budget, and wall-clock plus monotonic expiry. Expiry is rechecked after body processing and room-lock acquisition. Native callers may omit Origin; Origin is a browser boundary, not native authentication.

Both adapters accept only the exact literal loopback broker destination. The native client disables proxies and redirects, limits request time and streamed response size, and checks the configuration snapshot before and after receiving an offer. The browser omits ambient credentials/cookies, rejects redirects, bounds responses, and ties polling and file reads to cancellation/generation state. Failure does not automatically replay commands or consume a fresh grant. Noise still authenticates application traffic independently of the broker.

Host preparation creates a new mode-0700 directory and mode-0600 files. The browser invitation contains the Noise capability, authenticated context, and client signaling credential; host and broker files are separate. A local `.gitignore` excludes the directory contents as an accidental-commit guard, not a substitute for protecting or securely delivering the invitation. Intended signaling requests contain SDP and the appropriate role credential, never the password, Noise capability, host credential from the browser, or terminal input. SDP is opaque to the broker; this is not a promise to detect arbitrary secrets deliberately embedded by a caller.

The room's consumed state is in memory, and losing a consumed response requires fresh pairing. Restarting the broker with the same credentials does not create durable one-use semantics. The gateway's separate consumed-grant ledger remains the durable application boundary. These bounds do not establish public-service availability, global TCP connection limits, or remote connectivity. The review found no unresolved concrete blocker for this loopback increment after the fixes above.

## Authorized temporary LAN pilot review

The owner separately authorized a temporary Mac `192.168.1.147` to omarchy `192.168.1.198` test, with private invitation and password still required, no Internet exposure or persistent network changes, and shutdown afterward. The explicit `remote-answer-lan` command opts into this narrow test policy; existing commands and the transport default remain loopback-only. The implementation keeps trusted frontend assets on the client's loopback server, separate from credentials, and transfers invitation/SDP privately rather than exposing the host's HTTP password frontend to the LAN.

The native pilot binds one IPv4 UDP socket to the selected Mac address, enables UDP4 only, disables mDNS, and configures no STUN/TURN servers, wildcard gathering, or other local interfaces. It accepts only bounded numeric host-UDP candidate descriptions for the designated peer. Because candidate filtering does not itself prevent ICE peer-reflexive traffic, an additional application-level datagram wrapper discards other source IPs and rejects other destination IPs before ICE. This is defense in depth, not an OS firewall or cryptographic identity. Noise capability/context authentication and the principal-bound password remain the command-authority boundary.

The review found two teardown gaps in the first wrapper draft: a retained mux could keep the socket owner alive after its worker stopped, and a pending send could outlive the initial close-state check. The implementation now detaches a shared optional socket owner on cleanup, before awaiting peer closure, and observes the current close state during both receive and send. A fake-socket ownership regression holds the mux alive deliberately and verifies release after normal cleanup and aborted-future cleanup. Another regression proves close cancels an already-pending send and prevents any new underlying send. Closed receive paths and mixed permitted/forbidden candidates are covered without opening LAN sockets. The manual native offer and browser answer paths also now reuse the strict description validation previously added for automatic signaling.

The first two live attempts failed before password authentication. Bounded diagnostics identified native ICE failure at 30 seconds, before the manually transferred answer reached the client. Only the explicit LAN pilot now extends ICE's failure stage to 120 seconds (approximately 125 seconds including the upstream disconnected stage). Default loopback timing and post-connection disconnected behavior remain unchanged. The independently reviewed outer absolute grant/lifetime deadline still caps the entire operation at no more than ten minutes; the longer ICE stage does not extend application authority.

Diagnostics require both the explicit LAN policy and `HARBOR_LAN_DIAGNOSTICS=1`. Source inspection confirms output is limited to elapsed time, state enums, and saturating packet/error counters: at most 32 state lines, 44 power-of-two count lines, and one summary. These logs contain no packet payloads, SDP, credentials, commands, or addresses. The added tests cover diagnostic gating/counter saturation and the LAN-only timeout choice, alongside the existing expired-deadline/closed-dispatch tests. No firewall change or broader network policy was needed.

At the final LAN snapshot, **85 Rust tests** pass independently: 47 gateway tests plus 38 transport-workspace tests, including eleven transport host/policy/lifecycle tests. Root and transport formatting, frontend and physical-client harness JS syntax, and diff checks pass. The implementation owner's final loopback aggregate also passed after these changes, including both browser flows and separate-process snapshot revocation.

The implementation owner and physical-client worker reported a successful third attempt on the two real computers: Chromium selected `192.168.1.198:34860` to `192.168.1.147:54421`, completed Noise and assigned-principal password authentication, launched registered `/bin/cat`, verified terminal round-trip output from the actual xterm buffer, and completed Stop/logout. Native ICE and peer connection succeeded at about 37.7 seconds, consistent with the answer-transfer timing diagnosis. They verified native process/socket exit, browser/static-server shutdown, and disposable credential/SDP cleanup. A subsequent independent read-only `lsof` check found no matching Mac UDP 54421 or loopback TCP 7878/7879 sockets; native process exit is the implementation owner's verified result, not an independent process-status assertion here. This review did not independently operate or rerun the physical-browser proof; its evidence and harness are recorded in `VERIFICATION.md` and `tests/two-device/`. This establishes the tested LAN path, not Internet/NAT reachability or a completed Codex model task.

## CrabScape rendezvous compatibility and public-source review

The existing service source uses Matchbox 0.14 full-mesh signaling at `wss://crabscape-introducer.fly.dev`. It accepts `crabscape-` room names of at most 80 characters and logs room membership, including the room name. The new adapter uses that unchanged protocol and a separate `crabscape-crabbridge-` namespace with an independently generated 128-bit random locator. The 53-character room fits the existing service. It contains no principal, password, Noise capability, or session grant. The `crabbridge-v1` payload marker separates the application protocol from game messages. No game identity, lobby membership, peer UUID, ready message, or room secrecy grants terminal authority.

Unlike the local broker, this public service does not authenticate host/browser roles or guarantee one-use pairing. A participant knowing the room, or a malicious signaling operator, can disrupt negotiation, impersonate peer metadata, occupy the selected peer, or cause an attempt to be consumed. These availability limits are explicit. The independent context-bound Noise channel, private random capability, encrypted principal-bound password, typed authorization core, and host consumed-grant ledger remain the security boundary. Publicly readable source does not change that model. Passwords and terminal traffic are sent only after Noise authentication, never through Matchbox signaling.

The native CLI selects either the exact production WSS endpoint or an explicit exact loopback test endpoint; an invitation alone cannot select an arbitrary destination or switch native modes. The native WebSocket uses normal certificate validation, no proxy/redirect/reconnect logic, pre-parser frame/message limits, bounded events and writes, and grant/config-snapshot checks. The host joins first, pins one announced peer, accepts one offer, and owns a single-use answer publisher. Browser signaling validates closed payload schemas, protocol, sender, ordering, expiry, and UTF-8 byte limits. Completed signaling closes independently of the authenticated peer connection; failure before completion does not silently reconnect or replay commands.

The review identified an outgoing-browser-offer validation gap. The adapter now rejects malformed, wrong-type, extra-field, NUL-containing, or oversized offers before opening a WebSocket. Its no-contact regression also rejects unsupported destinations. Additional owned-task regressions cover dropping the answer publisher, revoking the config guard, and expiring the grant after offer receipt: each closes signaling without emitting an answer. Earlier tests cover duplicate identities/peers/offers, wrong senders/roles/protocols, unknown fields, unsupported binary frames, size limits, churn, and expiry/revocation while waiting.

Final independent checks passed **93 Rust tests**: 55 gateway/adapter tests and 38 transport-workspace tests, plus formatting and the browser no-contact validation suite. Fixed-port fixtures were run with exclusive loopback-port ownership; no production service was contacted. The implementation owner's aggregate, also rerun from the imported worktree, passed the actual local Matchbox 0.14 full-mesh browser exchange through Noise, password login, registered PTY, and logout. Its captured signaling excluded the private capability, password, principal, session grant, and terminal marker. A second valid-looking peer with the wrong private capability could not reach password login or tools. This browser evidence was run by the implementation owner, not independently repeated here. Compatibility with the existing service implementation is verified locally; live production-service reachability is not claimed.

The public integration is an isolated `tools/crabbridge` workspace. The inspected payload omits host configurations, invitations, passwords, consumed-grant ledgers, generated artifacts, and the old screenshot containing disposable SDP credentials. Personal runtime paths were removed, third-party notices retained, and accidental crate publication disabled. The browser build uses an explicit asset allowlist and publishes the peer UI into a local artifact, not the local HTTP username/password UI or host files. Packaging regressions cover exclusion of injected private files, stale artifact replacement, and preservation of a complete artifact after build failure. The component's JavaScript UI/test fixtures are explicitly scoped apart from the Rust game/art pipeline.

At that source-integration milestone, the existing introducer implementation/deployment workflow and game web-build composition were unchanged. The later source-only composition increment is reviewed below; the introducer remains unchanged. This review performs no production deployment or service modification. The standalone static artifact does not inherit the native HTTP server's CSP and other security headers; equivalent hosting policy and a trusted frontend publisher remain deployment requirements. No unresolved concrete blocker was found for the reviewed source integration and local compatibility milestone. This is not a live-service, public-hosting, or arbitrary-network clearance.

## Static composition and fail-closed hosting configuration review

The source now composes independently built game and bridge artifacts inside the existing lease-protected store transaction. All selected artifacts are validated before mutation: regular files/directories, no symbolic links, an index, and the exact workflow SHA. Component markers remain separate. Main publication rejects older/divergent component revisions; previews reject incomparable or stale preview heads. A lease conflict restarts from the latest store rather than reusing a stale composed tree. The game build itself and the existing introducer service are not altered by this assembly step.

The review found that the first game-selected cleanup removed the hosting-owned root `CNAME`. The final implementation preserves that file independently of component output and refuses to replace it from game artifacts. The regression now checks a game-only update with a conflicting artifact `CNAME`, as well as preservation of the unselected bridge and existing preview folders. Independent local tests pass for this case, artifact identity and missing-baseline failures, symlink and rollback rejection, real disposable bare-git store roundtrips, and concurrent independent component writers. These tests used local repositories only, not a production publish target.

New bridge artifact publication is separately disabled unless the Actions variable `CRABBRIDGE_PUBLISH_ENABLED` is exactly `true`; job admission, artifact selection and download are gated. This is not an unpublish switch. Existing bridge content can remain in the store and can be inherited by a preview baseline while new bridge publication is disabled. Independent classifier, protected-gate, packaging and publication-policy tests pass. No variable, repository permission, deployment or branch-protection setting was changed by this review.

The credential UI is disabled by HTML itself before JavaScript loads. Activation requires a top-level page, HTTPS except for explicit numeric-loopback development, no controlling service worker, and a same-document HEAD response with the closed documented CSP, frame restrictions, no-referrer, nosniff, no-store, restricted permissions policy and policy version. Production policy does not permit the development signaling endpoints. A controller-change listener is installed before the awaited policy check; a sticky lock prevents startup from unlocking after a change, including during WASM initialization. A later controller change clears the current connection, credentials, terminal and queued input and disables the controls.

The review found and coordinated fixes for extra overriding CSP directives, case-variant duplicate directive names, ambiguous repeated permissions declarations, omission of the documented no-store check, initially editable credential controls, and a service-worker startup race. The final parser normalizes directive names, rejects duplicates and additional directives, and compares the closed permissions policy. Independent pure header-policy tests pass. The independently rerun real Chrome packaged-page fixture passes nested asset/WASM loading with valid headers, refusal with missing/incomplete headers, disabled controls with JavaScript off, and sticky refusal when controller-change is delivered during a held HEAD response or after Ready. Those controller-change cases are deterministic synthetic lifecycle events, not a test of a hostile installed worker. The implementation owner's final full aggregate also passed the existing 93 Rust tests and browser transport/revocation flows after these changes.

These are conservative configuration and accidental-use safeguards, **not a cryptographic frontend trust anchor**. A HEAD result does not establish the actual navigation response headers, and compromised same-origin code can replace the guard or use application secrets. A URL path beneath the game is not an isolated origin. No service-worker registration was found in the inspected game source; stale or unrelated same-origin workers remain possible. GitHub Pages cannot directly provide the required custom response headers, so the current unconfigured production asset stays locked. No meta tag or `_headers` file is represented as equivalent enforcement. A trusted header-capable hosting arrangement remains an explicit deployment decision. No unresolved concrete blocker remains for this source-only composition/configuration increment; it does not clear live hosting or remembered credentials for use.

## Remembered-login design and inactive library checkpoint

Optional remembered browser authentication is requested but is not implemented or enabled by the preceding hosting changes. The recommended direction is a reviewed WebAuthn/passkey implementation with normal user presence rather than storing passwords, session tokens, reusable invitations, or inventing a new signing protocol. Non-extractable browser keys alone do not stop same-origin scripts from invoking them and are not a hardware or non-copyability guarantee.

Before activation is accepted, the design must specify the trusted origin and RP configuration, stable host scope distinct from the random per-invitation host ID, fresh-password and explicit opt-in enrollment, short-lived single-use challenges bound to the authenticated connection and purpose, device expiry, and host-side list/removal. Revocation must cover new authentication, existing device-authenticated commands, late launches and idle sessions. Persistent writes must be serialized across processes so a concurrent stale enrollment cannot resurrect a revoked credential. User/password lifecycle changes must invalidate the corresponding authority. The existing fresh private invitation and Noise boundary remain required unless separately redesigned and reviewed. No real device enrollment, browser permission change or personal credential persistence was performed during this review.

The subsequent partial experiment is an isolated library behind the non-default `experimental-device-auth` feature, not a host authentication path. It uses exact-version `webauthn-rs` passkey registration APIs and SQLite transactions, with no dangerous ceremony-serialization or credential-internals features. Source review confirms required user verification and attestation `none`; the origin is explicit HTTPS with an exact DNS RP match, not invitation-selected. The default binary, RPC, configuration and browser UI do not call the library. Independent default-library tests run no device code, and the default normal dependency tree contains neither WebAuthn nor SQLite.

Review of the first draft found that registration exclusions selected every user's credentials and unbounded revoked history, that the registration lifetime lacked the parent grant/connection boundary, and that an observed file/privacy fault could be reversed to reuse the same store handle. The fixes scope exclusion IDs to at most eight current-user active/unexpired credentials, bound IDs and stored records, attach a close latch and absolute grant deadline, cap ceremonies to that deadline, and permanently poison a handle after observed path/privacy failure. Registration state and password proofs are consumed rather than serialized. SQLite immediate transactions re-read user version/hash/active state, enforce per-user active-credential limits and global ID uniqueness, and preserve revoked ID reservations. Fixture records used to exercise these ledger policies are explicitly synthetic storage data, not accepted WebAuthn assertions.

At this checkpoint, the **seven feature-library tests passed independently**, along with feature-enabled all-target compilation, formatting and diff checks. They cover origin policy, current-password freshness, shared-store version visibility, monotonic updates, ledger privacy/schema/replacement refusal, scoped exclusion IDs, insertion limits/uniqueness, and stale-version insertion rejection. Direct ceremony tests additionally prove that a proof issued before close cannot begin enrollment, that a shorter grant caps the ceremony, and that wrong binding, expired state or a closed owner is rejected before processing an inert invalid WebAuthn response or inserting anything. CI explicitly runs these feature tests; default testing alone would omit them. The checkpoint's clonable owner required an explicit `close()` call: dropping a clone was not connection revocation. Reliable cleanup ownership, preferably a unique connection owner and non-owning leases, was required before runtime integration and is part of the subsequent change below.

At that inactive checkpoint, the library did **not** implement authentication completion, current-counter/backup-state handling, device list/removal, ordinary session issuance, command/late-launch/idle revocation hooks, or a browser virtual-authenticator success proof. The subsequent local integration is reviewed below. The persistent authority UUID and connection metadata are bookkeeping, not cryptographic host pinning or a completed Noise channel-binding design. File-identity checks assume a trusted host-owned filesystem and do not establish anti-rollback protection when a matching backup is restored before a new process opens it. Keeping an inactive, explicitly partial experiment was not clearance to enable remembered login or claim the requested feature was delivered.

## Optional passkey local integration review

The feature-enabled host now integrates standard passkey registration and authentication, host-side listing/removal, and current-principal browser management. The default binary still has no WebAuthn/SQLite dependency and rejects a configuration containing passkey settings rather than silently downgrading it. Activation additionally requires explicit host-admin configuration of an exact canonical HTTPS origin/RP and a new private absolute-path ledger. Each principal receives a distinct durable UUID under the ledger authority. The browser cannot choose the relying party, host identity, principal, database path or grants. No real user configuration or passkey was activated by this review.

Registration requires an authenticated idle session, an explicit browser action and verification of a freshly entered current password. Returning authentication uses the maintained WebAuthn verifier with required user verification, server-only single-use ceremony state, a fresh challenge, a sixty-second ceiling and the parent grant deadline. A fresh private Noise invitation remains necessary for every new connection. The frontend persists no password, bearer session or invitation; the deliberately registered credential is managed by the browser/platform authenticator. A synced passkey is not represented as a non-copyable physical-device identity.

The review found that the library's allowed-credential lookup did not compare an optional returned `userHandle` to the application user UUID. The wrapper now performs that exact check, while allowing `None` for non-discoverable credentials. Authentication re-reads the current user/hash/version and non-revoked, non-expired credential inside an immediate transaction, compares its exact serialized snapshot and updates counters/backup state using the library. A stale concurrent snapshot is rejected rather than overwriting newer state. Expiry is sampled again after acquiring the transaction and immediately before commit, not solely before cryptographic work. Revoked credential IDs remain reserved. Account replacement/removal invalidates the old UUID before saving the new configuration; a later file-save failure does not undo that revocation.

An opaque device proof is bound again at the core session-install boundary to the current principal, password hash, authority and exact remote grant. It cannot install a local HTTP session or transfer to another principal/grant. Current credential authority is checked before session installation, each terminal command, delayed launch installation and idle cleanup. Per-session read handles are opened outside the global authority lock; verification and writes run outside that lock, and liveness uses a nonblocking store mutex. SQLite busy waits are bounded, but filesystem I/O is not a realtime guarantee. A unique connection owner invalidates its leases on Drop and shares the connection's closed latch, which is checked before/after the lease lock and before mutation commits. Already accepted actions are not rolled back, and configuration files plus SQLite are not one atomic cross-process transaction.

The first expanded idle-revocation browser test exposed that dropping the transport future removed application authority without necessarily notifying the remote browser. The transport now owns an explicit shutdown path: it marks dispatch/authority closed, attempts graceful peer closure under a five-second bound while the UDP socket is usable, and unconditionally performs network cleanup afterward, including the timeout path. Setup/publisher waits also observe shutdown. The narrow LAN wrapper retains its cancellation-safe socket ownership cleanup; no additional LAN test or public-network activation was performed for this change.

Other review fixes bound remote inventory pages and serialized replies below the existing encrypted frame limit, make host listing IDs directly usable by removal, and close the connection on a canceled browser passkey prompt so stale server ceremony state cannot be mistaken for a usable retry. Epoch/abort guards discard late browser results after reset. Registration state is never serialized to the browser, and no production verification bypass was added for fixtures.

Independent verification passed the default **55** host tests, feature-enabled **57 host plus 10 device-library tests**, and the final **40 transport-workspace tests** (13 Noise, 14 broker and 13 transport/policy/lifecycle). The feature/transport set contains **107 unique Rust cases**; the default 55 overlap the feature host suite and are not added again. Formatting checks also pass. Synthetic storage records test transaction/counter mechanics only; the separate real-browser proof below supplies actual WebAuthn verification coverage.

The independently rerun Chrome fixture used a disposable virtual authenticator and a reserved HTTPS test origin served entirely through isolated request interception. It performed valid enrollment, a new private invitation and passwordless login, real registered `/bin/cat` input/output, Stop, listing/removal, cross-process revocation of an idle authenticated peer, and denial of the revoked credential on a fresh connection. Valid-credential assertions with changed user handle, challenge or origin, and an old assertion replayed into a new ceremony, received no tools. Canceled prompts, genuine pending-authenticator cancellation and a successful browser result delivered after reset did not enroll a credential; a fresh pairing could then retry successfully. The 390-pixel layout check also passed. The fixture reported no unexpected outbound application requests and cleaned its virtual authenticator, peers and disposable files.

This establishes the tested local passkey flow, not deployed HTTPS, a real personal passkey, a physical phone/carrier connection, public Internet reachability, or a new cryptographic host pin. Trusted invitation delivery and the existing Noise boundary remain essential. The static hosting and explicit Internet-network profiles require their own review and authorization; this passkey result does not activate either.

## Existing-introducer static frontend integration review

The next source increment mounts a compile-time allowlist of thirteen public assets at `/crabbridge/` in the existing Fly introducer. It does not put the host gateway, configuration, device ledger, invitation files or a login API in that service. Exact GET/HEAD asset routes, a fixed local canonical redirect, and plain 404/405 responses avoid filesystem access, uploads, query reflection and a catch-all application fallback. Static responses carry the reviewed production CSP and other deployment-policy headers, correct MIME types, no-store and no permissive CORS. Immutable embedded asset bytes are shared rather than copied into a new file-sized allocation on each request.

The existing game room and report routes retain their original room admission rules, CORS and report body limit. Inspection of Matchbox's builder confirms its CORS middleware is applied before the static router merge, not around the final application. The real ephemeral-loopback server regression exercises two-peer Matchbox relay, invalid/oversized room rejection, report coexistence and Origin-bearing static GET/HEAD responses with no CORS, frame denial and an empty HEAD body. Public assets are not secrets; absence of CORS is not an authentication mechanism.

Review found that making the frontend an unconditional introducer dependency would break clean-checkout game/co-op and mutation-test builds that do not package browser assets. The dependency is now default-off for those existing callers. Production Docker explicitly enables `crabbridge-frontend`; both bridge CI and the deployment workflow test feature-on routing as well as the default server. The public-only staging script creates a fresh directory from twenty-five explicitly named source/asset files, rejects file and parent-directory symlinks, refuses an existing output, and excludes injected private markers. Independent verification passed four frontend router tests, seventeen default introducer tests with a deliberately nonexistent asset directory, and eighteen feature-on introducer tests including the real local WebSocket/HTTP server. The seventeen default tests overlap the feature-on suite and are not additional unique cases. Frontend and feature-on introducer clippy, formatting, curated-context safeguards, component classification and public-asset packaging tests also passed. No container was deployed or provider contacted by these checks.

The Fly app's origin and publisher become trusted for executing the terminal frontend. The signaling messages remain untrusted inputs, but an operator or compromise that can replace frontend code can obtain credentials before encryption. Serving both roles from one origin does not create publisher independence; the deployment HEAD check is not an integrity proof. Existing qualifying-main deployment behavior is retained and expanded to relevant frontend changes, so a merge can deploy the new static route. This review does not authorize that merge or deployment, assert live HTTPS headers, or establish phone connectivity.

## Explicit direct-STUN source policy review

`DirectStun` is a separate, non-default host opt-in, not a relaxation of the loopback default or the previously authorized two-IP LAN socket filter. The host command, private invitation and transport policy must agree. The closed `context.network_profile` value is authenticated by the existing Noise prologue; omission preserves legacy serialized context. Unknown profiles and legacy/direct command mismatches fail closed. Direct mode requires the existing production Matchbox endpoint and rejects local broker/test metadata. Neither invitation nor browser can supply arbitrary native STUN/TURN URLs.

The only discovery servers are the game's two fixed Google STUN endpoints. Native transport is IPv4 UDP with mDNS disabled, no TURN or TCP fallback. Supplied candidates have bounded byte/count/extension schemas and must be public numeric UDP host/srflx destinations on non-privileged ports. Published descriptions omit unsupported candidate destinations and fail if no acceptable candidate survives. This is SDP input/output hygiene, not a traffic firewall: the maintained ICE implementation uses broad wildcard-bound ephemeral UDP for reflexive discovery and may receive untrusted or peer-reflexive packets. Related-address metadata can still reveal private addresses. Fixed STUN services and public signaling receive network metadata; Noise and the separate password/passkey authorization boundary continue to protect application traffic and tool access.

Review found that the browser initially performed discovery before checking an invitation's expiry window. The actual peer constructor now checks a safe-integer expiry and the remaining ten-minute bound immediately before creating `RTCPeerConnection`. A mock-constructor regression proves expired, invalid and excessive grants do not create a peer. This does not authenticate arbitrary invitation files before discovery; private trusted invitation delivery and the user's explicit connection action remain required.

Independent focused checks passed fourteen Noise tests, fifteen transport policy/lifecycle tests, the host command/profile rejection regression, and browser candidate/configuration/no-constructor safeguards. The profile mismatch test rejects a same-key handshake when only the network profile differs. Existing fake-socket lifecycle tests still pass; these checks neither invoke DirectStun gathering nor contact Google or production Matchbox. They are not a local STUN-server integration test or a cross-network connectivity proof. A separately approved live test must verify the actual selected route and complete teardown. Some mobile/carrier/symmetric NATs will not connect without a relay; no universal cellular, TURN or TLS-443 fallback is claimed.

## Next deployment boundary and broader hardening

The temporary LAN exception above uses trusted client-loopback assets and private manual signaling; it does not establish a generally hosted remote product. Beyond that exception, a usable remote deployment needs an owner-approved trusted HTTPS frontend/rendezvous origin and hosting arrangement, an explicit nonloopback ICE/network policy (including any STUN/TURN provider and costs), and actual target-device/network validation. Simply changing a bind address or reverse-proxying the local endpoints is not that design. Additional arbitrary loopback milestones are not a substitute for these choices. A narrow trusted-user pilot need not wait for a complete centralized host-daemon rewrite, but it must disclose snapshot-observation revocation, per-process resource bounds, and process-cleanup limits and review the concrete deployment changes before enabling them.

- Preserve and extend the existing connection-bound login, per-tool authorization, logout/revoke, close-during-work, expiry, and independent-principal safeguards tests as the deployment scope changes.
- Verify sockets, not merely advertised ICE candidates. Apart from the separately authorized temporary two-address LAN pilot above, this review authorizes no additional network exposure. No wildcard, STUN, TURN, public signaling, port forwarding, or public deployment is enabled by it.
- Preserve reviewed invitation consumption and revocation, and establish trusted frontend and invitation delivery for the pilot. Persistent host/device identity, password recovery, and device management require an additional reviewed design if the product adopts them. Secrets must not appear in URLs, browser storage, logs, source, or telemetry.
- Establish bounded handshake/setup deadlines, peer/channel counts, incoming data limits below parser allocation boundaries, transport backpressure, and resource cleanup under adversarial disconnect/retry patterns.
- Improve OS process-tree supervision. Current immediate-child cleanup is not a guarantee that descendants, detached daemons, or a registered tool's background work have stopped. Gateway revocation is not rollback. One controlled terminal per App is not a host-wide process limit. A 16-lifecycle budget now bounds active/pending/blocked-I/O cleanup per process and retains permits until every worker and immediate-child cleanup finishes. Bound the number of host processes operationally for a narrow trusted-user pilot; shared supervision and resource budgets are needed before broader multi-user availability claims.
- Broaden snapshot-revocation operational failure coverage. Actual separate HTTP/WebRTC process revocation after a host user-removal edit now passes the local browser proof. Command-time checks and 500 ms idle observation revoke old configurations without relying solely on process restart; restart is still required to accept the new configuration. Live granular reload and instantaneous shared host authority are not implemented.
- Audit pinned dependencies and browser/WASM asset provenance; run all final Rust/JS checks. No clean vulnerability scan or external library audit is implied by using established libraries.
- The specified physical LAN pair now passes. Test other target devices and restrictive networks before promising broader reachability. Signaling and TURN reliability are separate from endpoint authentication. Keep the Mac awake and connected while using the tool.
